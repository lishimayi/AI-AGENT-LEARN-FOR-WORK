## 1. 大模型是什么

### 1.1 一句话定义

**大模型（Large Language Model，LLM）** 是一种基于深度学习、在海量文本数据上训练出来的**超大规模神经网络**。它的核心能力是：**给定一段上下文，预测下一个最可能出现的词（Token）**，并由此延伸出对话、写作、推理、代码生成等能力。

你可以把它理解为：一个「读过互联网上几乎所有公开文本」的**概率化语言引擎**——它不真正「理解」世界，但极其擅长**模仿人类语言的统计规律**。

### 1.2 与相关概念的区别

| 概念 | 含义 | 与大模型的关系 |
|------|------|----------------|
| **人工智能（AI）** | 让机器表现出智能行为的广义领域 | 大模型是当前 AI 最主流的实现路径之一 |
| **机器学习（ML）** | 从数据中自动学习规律的方法 | 大模型属于深度学习分支下的 ML |
| **深度学习（DL）** | 使用多层神经网络的 ML | 大模型通常有数十到数千层 |
| **大模型（LLM）** | 参数量达到亿级以上的语言模型 | 本系列文档的核心对象 |
| **基础模型（Foundation Model）** | 预训练后可适配多种下游任务的通用模型 | GPT-4、Claude、GLM 等均属此类 |
| **AI Agent** | 能感知环境、做决策、调用工具的自主系统 | **大模型是 Agent 的「大脑」**，负责推理与规划 |

### 1.3 为什么叫「大」

「大」主要体现在三个维度：

```
┌─────────────┬──────────────────────────────────────────────────┐
│   维度      │   典型规模（2024–2026 头部模型）                  │
├─────────────┼──────────────────────────────────────────────────┤
│  参数量     │   70 亿 ~ 数万亿（如 GPT-4 据估 1.8T MoE）        │
│  训练数据   │   数 TB 级文本 + 代码 + 多模态数据                │
│  训练算力   │   数千 ~ 数万张 GPU，训练成本数千万美元级          │
└─────────────┴──────────────────────────────────────────────────┘
```

参数量越大，模型能「记住」的语言模式越丰富，涌现能力（Emergent Abilities）越明显——例如复杂推理、多步规划、工具调用等，在小模型上几乎不存在。

### 1.4 大模型能做什么

当前主流大模型的核心能力可归纳为：

| 能力 | 说明 | 典型场景 |
|------|------|----------|
| **文本生成** | 续写、创作、翻译、摘要 | 写作助手、邮件润色 |
| **对话交互** | 多轮上下文理解与自然回复 | 客服、个人助理 |
| **知识问答** | 基于训练知识回答开放问题 | 通用问答（有幻觉风险） |
| **代码生成** | 编写、解释、调试代码 | Copilot、代码审查 |
| **推理与规划** | 链式思考（CoT）、分步解题 | 数学、逻辑、Agent 决策 |
| **工具调用** | 按指令调用外部 API / 函数 | 查天气、查数据库、发邮件 |
| **多模态理解** | 图像、音频、视频输入 | 看图问答、文档 OCR |

> **重要认知**：大模型是**通用能力引擎**，不是数据库。它对训练截止日期之后的事件、你的私有业务数据，默认是不知道的——这正是 RAG、Function Calling 等 Agent 技术存在的原因。

### 1.5 LLM 三大核心能力

上表列举了 LLM 的多种应用形态；若从能力本质出发，可归纳为**三大核心能力**——它们层层递进，共同构成 Agent 的「大脑」：

```
┌─────────────────────────────────────────────────────────────┐
│                    LLM 三大核心能力                          │
│                                                             │
│   ① 语言理解          ② 语言生成          ③ 知识推理         │
│   Understanding  →   Generation    →   Reasoning          │
│   「读懂」            「说出」            「想清楚」           │
└─────────────────────────────────────────────────────────────┘
         │                    │                    │
         └────────────────────┴────────────────────┘
                    底层统一机制：
              Next Token Prediction（预测下一个词）
```

#### ① 语言理解（Language Understanding）

**定义**：从文本中抽取语义、识别用户意图、把握上下文关系的能力。

| 子能力 | 说明 | 示例 |
|--------|------|------|
| **语义理解** | 理解词句含义、情感、语气 | 「这条评论是差评还是 sarcasm？」 |
| **意图识别** | 判断用户想做什么 | 「帮我订机票」→ 订票意图 |
| **上下文追踪** | 多轮对话中记住前文 | 「它」指代上一轮提到的「苹果」 |
| **指令解析** | 理解任务要求与约束 | 「用 100 字以内、Markdown 格式总结」 |

**API 体现**：`messages` 数组中的 `system` / `user` / `assistant` 角色，模型需理解全部历史才能正确回复。多轮对话 demo 的核心就是维护好这段上下文。

**局限**：理解不等于「知道事实」——模型可以正确理解「2026 年世界杯冠军是谁」，但仍可能给出错误答案（幻觉）。

#### ② 语言生成（Language Generation）

**定义**：根据理解结果，产出连贯、符合要求、风格合适的文本（或代码）的能力。

| 子能力 | 说明 | 示例 |
|--------|------|------|
| **续写与创作** | 按主题生成新内容 | 写邮件、写故事、写报告 |
| **翻译与改写** | 跨语言或跨风格转换 | 中译英、口语改书面语 |
| **摘要与提取** | 压缩长文本为要点 | 长文档 TL;DR |
| **格式化输出** | 按指定结构生成 | JSON、Markdown 表格、代码块 |

**API 体现**：`completion` 阶段的自回归输出；`temperature` 控制创意程度；JSON Mode / Structured Output 约束格式。

**与理解的关系**：理解是「输入侧」，生成是「输出侧」。同一个模型、同一次 API 调用，两者同时发生——先理解 Prompt，再生成回复。

#### ③ 知识推理（Knowledge & Reasoning）

**定义**：运用训练中获得的知识，进行逻辑推断、多步规划、举一反三的能力——是 LLM 从「文本工具」升级为「智能助手」的关键。

| 子能力 | 说明 | 示例 |
|--------|------|------|
| **知识运用** | 调用训练语料中的事实与模式 | 「Python 列表推导式怎么写？」 |
| **逻辑推理** | 多步推导、因果分析 | 数学题、逻辑谜题、Bug 定位 |
| **上下文学习（ICL）** | 从 Prompt 中的示例学会新任务 | Few-shot：给 3 个例子，模型就会做第 4 个 |
| **链式思考（CoT）** | 分步展开推理再给出结论 | 「请一步步思考」后准确率显著提升 |
| **规划与决策** | 拆解复杂任务、决定执行顺序 | Agent 的任务分解与工具选择 |

**API 体现**：复杂 Prompt 设计（Few-shot、CoT）；推理模型（o1、DeepSeek-R1）内置更长思考链；Function Calling 中的「何时调工具、传什么参数」本质上是推理能力。

**局限**：知识来自训练语料，有**截止时间与幻觉风险**；复杂推理仍可能出错——Agent 场景需配合 RAG（补知识）和工具（补实时数据）。

#### 三大能力的关系与 Agent 映射

```
用户输入
    │
    ▼
┌──────────┐     ┌──────────┐     ┌──────────┐
│ 语言理解  │ ──→ │ 知识推理  │ ──→ │ 语言生成  │ ──→ 回复 / 工具调用
│ 读懂问题  │     │ 想清楚    │     │ 说出来    │
└──────────┘     └──────────┘     └──────────┘
                      │
                      ▼
              需要外部信息？
              ├─ 是 → RAG / 工具调用（Phase 3~4）
              └─ 否 → 直接生成
```

| 核心能力 | Agent 中的角色 | 本仓库对应 Phase |
|----------|----------------|------------------|
| 语言理解 | 解析用户意图、理解工具返回结果 | Phase 1~2（API + Prompt） |
| 语言生成 | 组织最终回复、生成结构化输出 | Phase 2（Prompt 工程） |
| 知识推理 | 任务规划、工具选择、多步决策 | Phase 3~5（工具调用 + Agent 框架） |

> **一句话记忆**：LLM 先**读懂**你在说什么，再**想清楚**该怎么答，最后**说出来**——对话、写代码、调工具，都是这三步的不同组合。

### 1.6 什么是 Token

**Token** 是大模型处理文本时的**最小单位**——但不是「一个字」，也不完全等于「一个词」。你可以把它理解为：模型把句子**切成了若干小块**，每一块就是一个 Token。

#### 一句话定义

> **Token = 模型「读」和「写」文本的基本单元，对应词表中的一个编号（Token ID）。**

模型不认识汉字或英文字母，只认识数字。Tokenizer（分词器）负责把人类语言翻译成这些数字：

```
「你好，世界」  ──Tokenizer──→  [你, 好, ，, 世界]  ──编码──→  [872, 196, 11, 4518]
   人类文本                        Token 序列                    Token ID（数字）
```

#### Token ≠ 字，Token ≠ 词

| 对比 | 说明 | 示例 |
|------|------|------|
| **Token vs 汉字** | 1 个汉字通常是 1~2 个 Token | 「人工智能」可能是 2 个 Token：`人工` + `智能` |
| **Token vs 英文词** | 1 个英文单词通常是 1 个 Token | `hello` → 1 Token；`unhappiness` 可能拆成 `un` + `happiness` |
| **标点、空格** | 也占 Token | `你好，` 中的逗号单独算 1 个 Token |
| **代码** | 符号、缩进、换行都占 Token | 一段 Python 的 Token 数往往比「字数」多很多 |

常见分词示例：

```
文本              切分结果（Token）
─────────────────────────────────────
"ChatGPT"         ["Chat", "G", "PT"]        → 3 个 Token
"人工智能"         ["人工", "智能"]            → 2 个 Token
"Hello world"     ["Hello", " world"]        → 2 个 Token
"def add(a, b):"  ["def", " add", "(", "a", ",", " b", "):", ...]  → 更多
```

#### 为什么开发者必须理解 Token

Token 不是纯理论概念，它直接决定**三件事**：

| 影响 | 说明 | 举例 |
|------|------|------|
| **💰 计费** | API 按 Token 数收费，不是按字数 | 输入 1000 Token + 输出 500 Token = 共 1500 Token 计费 |
| **📏 上下文窗口** | 模型一次最多处理 N 个 Token | 128K 窗口 ≈ 8~10 万汉字，不是 128 万个字 |
| **✂️ 截断** | 超出窗口的内容会被截掉或报错 | 长对话需要裁剪历史 |

一次 API 调用返回的 `usage` 字段：

```json
{
  "usage": {
    "prompt_tokens": 42,       // 你发送的内容（含 system + 历史 + user）
    "completion_tokens": 128,  // 模型生成的回复
    "total_tokens": 170        // 合计，通常用于计费
  }
}
```

仓库 `open_api_demo.py` 会本地估算 `prompt_tokens`，再与接口返回的 `usage` 对比——帮助你建立 Token 成本直觉。

#### 中英文 Token 效率差异

不同语言的 Token 密度不同，**同样信息量，中文往往比英文更「费 Token」**：

| 内容 | 大约 Token 数 | 直觉 |
|------|--------------|------|
| 100 个英文单词 | ~130 Token | 1 个英文词 ≈ 1~1.3 Token |
| 100 个汉字 | ~150~200 Token | 1 个汉字 ≈ 1.5~2 Token |
| 100 行 Python | ~800~1200 Token | 代码符号多，密度高 |

因此：**用中文对话比英文略贵，长代码 Prompt 要特别关注 Token 消耗**。

#### 实战案例：《红楼梦》长文本 Token 与成本

用一个真实的长文本建立 Token 与**钱**的直觉——《红楼梦》全书：

| 指标 | 数值 |
|------|------|
| **原文字数** | 约 **73 万字**（各版本略有出入） |
| **折算 Token** | 约 **50 ~ 60 万** Token |
| **换算比例** | 1 Token ≈ 1.2 ~ 1.5 个汉字（古典白话，因 Tokenizer 而异） |

```
73 万字  ÷  1.2 ~ 1.5 字/Token  ≈  50 ~ 60 万 Token
```

**典型场景**：把全书作为 Prompt 输入，让模型做摘要、问答或分析（例如「请总结各回要点」）。费用取决于**输入 Token + 输出 Token**，不同厂商单价差一个数量级以上。

##### 费用对比（估算）

> 单价随模型版本、厂商调价而变化，以下为 **2025–2026 常见 API 档位** 的粗算，用于建立量级感；实际上线前请查[各厂商最新定价](https://api-docs.deepseek.com/zh-cn/quick_start/pricing)。

| 项目 | DeepSeek（V4-Flash 档） | ChatGPT（GPT-4o 档） |
|------|-------------------------|----------------------|
| **输入单价** | 约 1 元 / 百万 Token | 约 $2.5 / 百万 Token（≈ 18 元） |
| **输出单价** | 约 2 元 / 百万 Token | 约 $10 / 百万 Token（≈ 72 元） |
| **输入 55 万 Token** | 55 万 × 1 元/M ≈ **0.55 元** | 55 万 × 18 元/M ≈ **10 元** |
| **若再生成 5 万字回复（~6 万 Token）** | 6 万 × 2 元/M ≈ **0.12 元** | 6 万 × 72 元/M ≈ **4.3 元** |
| **合计（输入全书 + 中等长度输出）** | **约 1 ~ 2 元** | **约 15 ~ 20 元** |
| **若输出更长（接近输入量级）** | 仍约 **数元** | 可轻松到 **60 元+** |

**心算公式**：

```
费用 ≈ (输入 Token ÷ 1,000,000 × 输入单价) + (输出 Token ÷ 1,000,000 × 输出单价)
```

**《红楼梦》案例的一句话结论**：

> 同样处理 ~50–60 万 Token 的长文本，**DeepSeek 约 1–2 元，ChatGPT（GPT-4o）往往要 60 元量级**——差距主要来自**单价**，不是 Token 数不同。中文长文档、RAG 全量灌入、历史对话堆积时，这种差距会被放大。

##### 为什么差距这么大？

| 原因 | 说明 |
|------|------|
| **单价差** | DeepSeek 输入约 1 元/M；GPT-4o 输入约 18 元/M，相差约 **18 倍** |
| **输出更贵** | 各厂商输出 Token 单价通常是输入的 **2~5 倍**，长回复比短 Prompt 更烧钱 |
| **长文本场景** | 50 万 Token 在短对话里不常见，但在**全书分析、知识库灌入**里一次就到 |
| **Tokenizer 差异** | 同一本书，不同厂商 Token 数可能差 10%~20%，但单价差异才是主因 |

##### 对 Agent 开发的启示

| 场景 | 建议 |
|------|------|
| 长文档 QA / RAG | 不要全文塞进 Prompt，用检索只送相关片段 |
| 模型选型 | 摘要、分类等「够用即可」的任务可优先 DeepSeek 等低价 API |
| 成本监控 | 每次调用记录 `usage.total_tokens`，长文本任务单独做预算 |
| 旗舰模型 | GPT-4o / Claude 等留给复杂推理，与低价模型**混合路由** |

```python
# 长文本调用后务必打印 usage，避免「一本书烧掉几十元」的意外
response = client.chat.completions.create(model="glm-4-plus", messages=messages)
u = response.usage
print(f"输入 {u.prompt_tokens:,} + 输出 {u.completion_tokens:,} = 合计 {u.total_tokens:,} Token")
# 再用：合计 Token × 单价 ≈ 本次费用
```

#### Token 与模型行为的关系

```
你写的 Prompt（文本）
        │
        ▼  切成 N 个 Token
模型逐个「读」这 N 个 Token（Prefill 阶段）
        │
        ▼  再逐个「写」出 M 个 Token（Decode 阶段）
模型回复（文本）
        │
        ▼  解码
你看到的回答
```

- 模型**预测的是「下一个 Token」**，不是下一个字或词（见 §1.7）
- 流式输出（Streaming）就是每生成 **1 个 Token** 就推送一次——所以你看到「逐字蹦出」的效果
- `max_tokens` 参数限制的是**最多生成多少个 Token**，不是多少个字

#### 与 API Key 的区分（易混淆）

| 概念 | 含义 |
|------|------|
| **Token（文本单元）** | 模型处理文本的最小单位，用于计费与上下文（见上文） |
| **API Key** | 访问接口的**密钥字符串**，如 `sk-xxxx`，与文本 Token **完全无关** |

日常说「这次调用用了多少 Token」指前者；说「配置 API Key」指后者。API Key 的完整说明见 **§1.11**。

#### 如何估算 Token 数量

开发中经常需要在发送请求前知道「这段 Prompt 有多长」，常用三种方式：

| 方式 | 说明 | 适用 |
|------|------|------|
| **API 返回 `usage`** | 调用后从响应读取，最准确 | 已有请求、对账计费 |
| **本地 Tokenizer** | 用 Hugging Face / tiktoken 离线计算 | 发送前预估、控成本 |
| **在线估算工具** | OpenAI [Tokenizer](https://platform.openai.com/tokenizer) 等网页 | 快速试算、无代码 |

**方式一：读 API 返回（推荐对账）**

```python
response = client.chat.completions.create(model="glm-4-plus", messages=messages)
print(response.usage.prompt_tokens)      # 输入 Token 数
print(response.usage.completion_tokens)  # 输出 Token 数
print(response.usage.total_tokens)     # 合计
```

**方式二：本地预估（推荐发送前）**

本仓库 `open_api_demo.py` 在请求前先本地算一遍，再与接口 `usage` 对比：

```python
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("bert-base-chinese")  # 或与目标模型接近的 tokenizer
text = "你好，请介绍一下大模型中的 Token 是什么。"
token_ids = tokenizer.encode(text)
print(f"约 {len(token_ids)} 个 Token")  # 注意：与厂商官方计数可能有偏差
```

> **注意**：本地 Tokenizer 与厂商官方 Tokenizer 往往不完全一致，本地值用于**粗估**；精确计费以 API 返回的 `usage` 为准。

**方式三：经验速算（无工具时）**

| 文本类型 | 粗算规则 |
|----------|----------|
| 中文 | 字数 × 1.5 ~ 2 ≈ Token 数 |
| 英文 | 单词数 × 1.3 ≈ Token 数 |
| 混合 Prompt | 偏保守估算，预留 20% 余量 |

#### 常见问题

| 问题 | 答案 |
|------|------|
| 一个汉字 = 一个 Token 吗？ | **不是**。通常 1 字 ≈ 1.5~2 Token，因分词方式而异 |
| 空格、换行算 Token 吗？ | **算**。空白符也会被编码 |
| 图片 / 文件算多少 Token？ | 多模态模型按各自规则折算（如 patch、tile），与纯文本不同 |
| 对话历史算不算 Token？ | **算**。`messages` 里所有轮次都计入 `prompt_tokens` |
| 怎么省 Token？ | 精简 System Prompt、裁剪旧历史、摘要压缩长文档 |

> 分词算法（BPE）、不同厂商 Tokenizer 差异等深入内容，见 **§2.2 Token：模型眼中的「词」**。

### 1.7 大模型如何工作（通俗版）

无论厂商如何命名，现代大模型的底层逻辑高度一致：

```
用户输入（Prompt）
      │
      ▼
┌─────────────────┐
│  Tokenizer      │  文本 → 数字序列（Token ID）
└────────┬────────┘
         ▼
┌─────────────────┐
│  Transformer  │  多层注意力机制，理解 Token 之间的关系
│  神经网络       │
└────────┬────────┘
         ▼
┌─────────────────┐
│  输出概率分布    │  预测「下一个 Token 是什么」
└────────┬────────┘
         ▼
  逐个生成 Token，直到结束
         │
         ▼
  解码为可读文本 → 返回给用户
```

**Next Token Prediction（下一个词预测）** 是核心训练目标：给定 `「今天天气」`，模型预测下一个 Token 可能是 `「很」`；再给定 `「今天天气很」`，预测 `「好」`……如此循环，最终输出完整句子。

对话、推理、写代码，本质上都是**在同一条预测链上**，通过不同的 Prompt 引导模型走向不同的 Token 序列。

### 1.8 大模型的主要类型

| 类型 | 代表模型 | 特点 |
|------|----------|------|
| **纯文本 LLM** | GPT-4o、Claude 3.5、GLM-4 | 以文本输入输出为主，API 最成熟 |
| **多模态模型** | GPT-4o、Gemini 1.5、Qwen-VL | 同时处理文本、图像、音频等 |
| **代码专用模型** | Codex、DeepSeek-Coder、StarCoder | 在代码语料上强化训练 |
| **Embedding 模型** | text-embedding-3、BGE、M3E | 将文本转为向量，用于 RAG 检索 |
| **推理增强模型** | o1、o3、DeepSeek-R1 | 内置更长思考链，擅长复杂推理 |

### 1.9 开源模型 vs 闭源模型

按**是否公开模型权重与训练细节**，大模型分为开源和闭源两大阵营——这是选型时与「能力类型」「接入方式」并列的第三个重要维度。

```
                    大模型分类（三个独立维度）
    ┌─────────────────┬─────────────────┬─────────────────┐
    │  按能力          │  按开放程度      │  按接入方式      │
    │  文本/多模态/代码 │  开源 / 闭源     │  API / 本地部署  │
    └─────────────────┴─────────────────┴─────────────────┘
```

#### 开源模型（Open Source / Open Weights）

**定义**：模型权重对外公开，允许下载、本地部署、微调（具体权限以各模型 License 为准）。

| 项目 | 说明 |
|------|------|
| **公开内容** | 模型权重（.safetensors / .gguf 等）、架构说明、推理代码 |
| **通常不公开** | 完整训练语料、全部训练细节、对齐数据 |
| **典型 License** | Apache 2.0、MIT、Llama Community License、DeepSeek License |
| **代表模型** | LLaMA 3、Qwen 2.5/3、DeepSeek-V3/R1、Mistral、GLM-4（部分版本） |

**优势**：

- 可**本地部署**，数据不出境，满足隐私与合规要求
- 可基于业务数据**微调**（LoRA / 全量微调）
- **无 API 调用费**，高并发场景长期成本更低
- 社区生态活跃，工具链成熟（Ollama、vLLM、llama.cpp）

**劣势**：

- 需要自备 **GPU 服务器**，运维成本高
- 同等能力下，开源模型通常略逊于头部闭源模型
- 超大模型（405B+）本地部署门槛极高

#### 闭源模型（Closed Source / Proprietary）

**定义**：模型权重不公开，仅通过厂商提供的 **API 或托管服务** 调用。

| 项目 | 说明 |
|------|------|
| **公开内容** | API 文档、部分技术博客、基准测试成绩 |
| **不公开** | 模型权重、架构细节、训练语料、参数量 |
| **代表模型** | GPT-4o / o1 / o3、Claude 3.5/4、Gemini 1.5/2.0、GLM-4-Plus（API 版） |

**优势**：

- **能力上限高**，头部闭源模型在复杂推理、Agent 等场景通常领先
- **零运维**，注册 API Key 即可使用，自动扩容
- 厂商持续迭代，无需自行升级权重
- 配套生态完善（Function Calling、Embedding、Fine-tuning API）

**劣势**：

- **按 Token 计费**，大规模调用成本需精细管控
- 数据需传输至厂商服务器，有隐私与合规顾虑
- 依赖厂商可用性，存在速率限制、政策变更风险
- 国内部分厂商需代理访问

#### 开源 vs 闭源对比

| 维度 | 开源模型 | 闭源模型 |
|------|----------|----------|
| **权重** | 公开可下载 | 不公开 |
| **使用方式** | 本地部署 / 自建 API | 厂商云端 API |
| **数据隐私** | 高（数据不出本地） | 依赖厂商政策 |
| **能力上限** | 接近但通常略低 | 头部模型领先 |
| **成本模型** | GPU 硬件 + 电费 | 按 Token 付费 |
| **微调** | 自由微调 | 部分提供 Fine-tuning API |
| **运维** | 需自行维护 | 厂商托管 |
| **适合谁** | 有 GPU 资源、数据敏感、长期高并发 | 快速上线、追求最强能力、无 GPU |

#### 混合模式：「开源权重 + 商业 API」

越来越多厂商采取**双轨策略**——同一模型家族，既开源权重，又提供云端 API：

| 厂商 | 开源版本 | API 版本 | 说明 |
|------|----------|----------|------|
| **阿里通义** | Qwen 2.5/3（Hugging Face） | DashScope API | 开源可本地跑，API 免运维 |
| **DeepSeek** | DeepSeek-V3/R1 权重 | DeepSeek API | 开源 + 极低 API 单价 |
| **智谱** | GLM-4 部分开源 | GLM-4-Plus API | 本仓库默认用 API 版 |
| **Meta** | LLaMA 3 全系列开源 | 无官方 API | 仅开源，需自行部署 |
| **OpenAI** | 无 | GPT-4o / o1 等 | 纯闭源 |

```
                    ┌─────────────────────────────┐
                    │         你的应用           │
                    └──────────┬────────────────┘
                               │
              ┌────────────────┼────────────────┐
              ▼                                 ▼
    ┌──────────────────┐              ┌──────────────────┐
    │  云端 API 调用     │              │  本地 / 私有云部署  │
    │  （闭源或混合厂商） │              │  （开源权重）       │
    │  OpenAI / 智谱等   │              │  Ollama / vLLM    │
    └──────────────────┘              └──────────────────┘
         免运维、按量付费                  数据私有、固定成本
```

#### 开发者如何选

| 场景 | 推荐 |
|------|------|
| 学习、原型验证 | 闭源 API（本仓库：智谱 GLM），零门槛 |
| 生产环境、国内合规 | 闭源 API（智谱 / 通义 / DeepSeek API）或开源本地部署 |
| 数据绝不能出境 | 开源本地部署（Qwen / DeepSeek / LLaMA） |
| 追求最强推理能力 | 闭源 API（GPT-4o、Claude、DeepSeek-R1 API） |
| 高并发、成本敏感 | 开源本地部署，或 DeepSeek 等低价 API |
| 领域微调（医疗、法律等） | 开源模型 + LoRA 微调 |

> **本仓库 Phase 1 默认路径**：先用**闭源/混合厂商的 API**（智谱 GLM）完成接入与对话；待 Phase 7 或确有隐私需求时，再探索开源本地部署。两条路径的 Prompt、Token 计量逻辑完全一致。

### 1.10 接入大模型的渠道

作为开发者，接入大模型有多种路径。可按**谁提供算力、谁暴露接口**分为六大渠道——本 Part 1 以**渠道 ① 官方 API** 为主，其余渠道在进阶与生产阶段按需选用。

```
                         接入大模型的六大渠道
    ┌────────────────────────────────────────────────────────────┐
    │  ① 厂商官方 API     ② 云平台托管     ③ API 聚合平台        │
    │  ④ 本地 / 私有部署   ⑤ HF 等托管推理  ⑥ Agent 框架路由     │
    └────────────────────────────────────────────────────────────┘
                              │
                    统一目标：拿到「模型推理能力」
                    输入 messages → 输出 completion
```

#### 渠道总览

| 渠道 | 说明 | 典型代表 | 适合场景 |
|------|------|----------|----------|
| **① 厂商官方 API** | 直接向模型厂商注册 Key，调用官方 HTTP 接口 | OpenAI、智谱、Anthropic、DeepSeek | 学习、原型、国内生产（本仓库默认） |
| **② 云平台托管** | 通过云厂商购买的「模型即服务」，企业合规与账单统一 | Azure OpenAI、AWS Bedrock、阿里云百炼、Vertex AI | 企业上云、已有云账号、需 SLA |
| **③ API 聚合平台** | 一个 Key 访问多家模型，统一计费与路由 | OpenRouter、Together AI、Groq | 快速对比多模型、海外模型聚合 |
| **④ 本地 / 私有部署** | 在自有机器或内网 GPU 上运行开源权重 | Ollama、vLLM、llama.cpp、LocalAI | 数据不出境、离线、高并发控本 |
| **⑤ 托管推理服务** | 第三方帮你托管开源模型，你只调 API | Hugging Face Inference、Replicate、Fireworks | 不想运维 GPU，又要开源模型 |
| **⑥ Agent 框架路由** | 框架封装多后端，代码层切换模型 | LangChain、LlamaIndex、Dify | 多模型切换、工作流编排 |

#### ① 厂商官方 API（推荐入门）

**最常用、最直接**的接入方式：在厂商开放平台注册账号 → 创建 API Key → HTTP 请求或 SDK 调用。

| 厂商 | 接入入口 | Base URL（OpenAI 兼容） | 本仓库 |
|------|----------|-------------------------|--------|
| **智谱 AI** | [open.bigmodel.cn](https://open.bigmodel.cn/) | `https://open.bigmodel.cn/api/paas/v4/` | ✅ 默认 |
| **OpenAI** | [platform.openai.com](https://platform.openai.com/) | `https://api.openai.com/v1` | 需代理 |
| **DeepSeek** | [platform.deepseek.com](https://platform.deepseek.com/) | `https://api.deepseek.com/v1` | 低价备选 |
| **Anthropic** | [console.anthropic.com](https://console.anthropic.com/) | 自有 SDK（非 OpenAI 格式） | Claude 专用 |
| **阿里通义** | [dashscope.aliyun.com](https://dashscope.aliyun.com/) | 兼容模式可用 OpenAI SDK | 国内备选 |
| **Google Gemini** | [ai.google.dev](https://ai.google.dev/) | 自有 SDK / REST | 多模态 |

**调用链路**：

```
你的代码（Python / Node / curl）
        │
        ▼  HTTPS + Authorization: Bearer <API_KEY>
厂商 API 网关
        │
        ▼

        │
        ▼

```

```python
    base_url="https://open.bigmodel.cn/api/paas/v4/",
)

    model="glm-4-plus",

```

| 优点 | 缺点 |
|------|------|
| 注册即用，零 GPU 运维 | 按 Token 计费，用量大需控成本 |
| 文档与 SDK 完善 | 数据经厂商服务器 |
| 模型持续更新 | 受速率限制（RPM/TPM）影响 |

#### ② 云平台托管（企业常见）

将大模型作为**云产品**购买，账单、权限、VPC 与现有云资源统一管理。

| 平台 | 提供模型 | 特点 |
|------|----------|------|
| **Azure OpenAI** | GPT-4o、o1 等 | 微软企业合规，与 Azure AD 集成 |
| **AWS Bedrock** | Claude、Llama、Titan 等 | 多模型一站式，IAM 权限体系 |
| **Google Vertex AI** | Gemini 系列 | GCP 生态，企业 SLA |
| **阿里云百炼** | 通义 Qwen、三方模型 | 国内合规，与阿里云账号打通 |
| **腾讯云 TI** | 混元等 | 国内政企常见 |
| **火山引擎** | 豆包等 | 字节系，与火山云集成 |

```
企业应用 → 云 VPC 内网 → 云平台模型 endpoint → 不经过公网直连厂商
                ↑
         统一账单 / 审计 / 权限
```

| 优点 | 缺点 |
|------|------|
| 企业合规、SLA、私有网络 | 开通流程长，常需商务合同 |
| 与现有云 IAM / 日志集成 | 部分模型版本滞后于官方 |
| 适合已有云采购的团队 | 报价比直连官方略高 |

---

#### ③ API 聚合平台

**一个 API Key 访问多家模型**，聚合器负责路由、计费与 failover。

| 平台 | 特点 |
|------|------|
| **[OpenRouter](https://openrouter.ai/)** | 模型最全，OpenAI 兼容，按模型标价（下文详述） |
| **[Together AI](https://www.together.ai/)** | 开源模型推理为主 |
| **[Groq](https://groq.com/)** | 自研 LPU，极低延迟 |
| **国内类似服务** | 部分中转平台（需注意合规与稳定性） |

##### OpenRouter 详解

**OpenRouter** 是目前最主流的 **LLM API 聚合平台**之一：注册一个账号、创建一个 API Key，即可通过**同一套 OpenAI 兼容接口**调用 GPT、Claude、Gemini、Llama、DeepSeek 等数百个模型，无需分别去各厂商开户。

**一句话定位**：

> OpenRouter = **一个大模型「应用商店」+ 统一收银台**——你选模型 ID，它帮你路由到对应厂商并代扣费用。

**工作原理**：

```
你的代码（openai SDK）
        │
        ▼  base_url = openrouter.ai/api/v1
┌───────────────────┐
│    OpenRouter     │  ← 一个 Key、统一账单
│    路由 / 计费     │
└─────────┬─────────┘
          │ 按 model ID 转发
    ┌─────┼─────┬─────────┐
    ▼     ▼     ▼         ▼
 OpenAI Claude Gemini  DeepSeek …
```

**核心特点**：

| 特点 | 说明 |
|------|------|
| **OpenAI 兼容** | 完全兼容 Chat Completions 格式，直接用 `openai` Python SDK |
| **模型极全** | 覆盖 OpenAI、Anthropic、Google、Meta、Mistral、DeepSeek 等 |
| **按模型计价** | 每个模型独立标价，可在 [openrouter.ai/models](https://openrouter.ai/models) 查询 |
| **按量付费** | 充值 Credits，用多少扣多少，无月费 |
| **便于对比** | 同一 Prompt 换 `model` 字符串即可 A/B 测试 |
| **自动 Failover** | 部分模型支持备用路由（视平台配置而定） |

**接入步骤**：

1. 打开 [openrouter.ai](https://openrouter.ai/) 注册账号  
2. 进入 **Keys** 页面创建 API Key  
3. 充值 Credits（支持信用卡等，国内用户需注意支付方式）  
4. 在 [Models](https://openrouter.ai/models) 页查目标模型的 **Model ID**  
5. 代码里改 `base_url` + `model` 即可调用  

**代码示例（与本仓库 SDK 方式一致）**：

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("OPENROUTER_API_KEY"),
    base_url="https://openrouter.ai/api/v1",
)

response = client.chat.completions.create(
    # Model ID 格式：厂商/模型名，在 OpenRouter 模型页复制
    model="anthropic/claude-3.5-sonnet",
    messages=[{"role": "user", "content": "用三句话解释什么是 Token"}],
    extra_headers={
        "HTTP-Referer": "https://your-app.com",  # 可选，用于 OpenRouter 排行统计
        "X-Title": "AI Agent Learn",             # 可选，你的应用名称
    },
)
print(response.choices[0].message.content)
print(response.usage)
```

**环境变量配置（`.env`）**：

```bash
# OpenRouter（与智谱 Key 分开存放，按场景切换）
OPENROUTER_API_KEY=sk-or-v1-xxxxxxxx
```

**常用 Model ID 示例**（以 OpenRouter 模型页为准，名称会随版本更新）：

| 模型 | OpenRouter Model ID | 典型用途 |
|------|---------------------|----------|
| GPT-4o | `openai/gpt-4o` | 综合能力强、生态标准 |
| Claude 3.5 Sonnet | `anthropic/claude-3.5-sonnet` | 长文本、代码、写作 |
| Gemini 1.5 Pro | `google/gemini-pro-1.5` | 多模态、超长上下文 |
| DeepSeek V3 | `deepseek/deepseek-chat` | 高性价比、中文友好 |
| Llama 3.1 70B | `meta-llama/llama-3.1-70b-instruct` | 开源档、试验对比 |

**与官方 API 直调对比**：

| 维度 | OpenRouter | 厂商官方 API |
|------|------------|--------------|
| **开户** | 一个账号调所有模型 | 每家厂商单独注册、单独 Key |
| **代码** | 换 `model` 即可切模型 | 换 `base_url` + Key + 可能换 SDK |
| **价格** | 通常略高于官方，含聚合服务费 | 官方标价，有时更便宜 |
| **延迟** | 多一跳路由，略增 | 直连，通常更低 |
| **数据路径** | 请求经 OpenRouter 中转 | 直连厂商（视厂商政策） |
| **国内访问** | 视网络环境，可能需要代理 | 国内厂商（智谱等）直连更稳 |
| **适合** | 海外模型对比、原型、个人开发 | 国内生产、企业合规、大规模稳定调用 |

**适用场景**：

| 场景 | 是否推荐 OpenRouter |
|------|---------------------|
| 快速试用 GPT / Claude，不想分别注册 | ✅ 强烈推荐 |
| 同一任务对比 3~5 个模型效果 | ✅ 强烈推荐 |
| 国内生产环境、低延迟要求 | ⚠️ 优先考虑智谱 / DeepSeek 官方 API |
| 敏感数据、金融医疗合规 | ⚠️ 数据经第三方，需评估隐私政策 |
| 长期高并发、成本极致优化 | ⚠️ 官方直调或 DeepSeek 通常更划算 |

**与本仓库的关系**：

```
Phase 1 默认：智谱官方 API（国内直连、学习成本低）
        │
        ▼  掌握 base_url + api_key + model 三要素后
可选进阶：OpenRouter 一条 Key 试遍海外模型，代码结构不变
```

切换只需改 Client 初始化，业务逻辑（`messages`、流式、`usage`）完全复用：

```python
# 智谱（默认）
client = OpenAI(api_key=os.getenv("ZHIPUAI_API_KEY"),
                base_url="https://open.bigmodel.cn/api/paas/v4/")

# OpenRouter（对比海外模型时）
client = OpenAI(api_key=os.getenv("OPENROUTER_API_KEY"),
                base_url="https://openrouter.ai/api/v1")
```

**注意事项**：

- Model ID 必须带**厂商前缀**（如 `openai/`、`anthropic/`），与官方 API 的 `gpt-4o` 写法不同  
- 价格以 OpenRouter 模型页为准，**会随官方调价变化**  
- 部分模型的 Function Calling、JSON Mode、Vision 能力取决于底层模型是否支持

### 1.11 什么是 API Key

**API Key**（Application Programming Interface Key）是调用大模型云端接口时的**身份凭证**——相当于你的「账号密码」，证明「这次请求是你发起的、费用记在你账上」。

#### 一句话定义

> **API Key = 一串由厂商颁发的密钥，每次请求时携带，用于鉴权与计费。**

没有 API Key，请求会被拒绝（401 Unauthorized）；Key 泄露，别人可以用你的余额调模型。

#### 长什么样

各厂商格式略有不同，通常是**一长串随机字符**：

```
sk-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
│
└─ 常见前缀（OpenAI 风格）；智谱、DeepSeek 等也类似
```

| 厂商 | Key 示例格式 | 在哪创建 |
|------|-------------|----------|
| **智谱 AI** | 一串字母数字 | [open.bigmodel.cn](https://open.bigmodel.cn/) → API Keys |
| **OpenAI** | `sk-proj-...` 或 `sk-...` | platform.openai.com → API keys |
| **DeepSeek** | `sk-...` | platform.deepseek.com → API Keys |
| **阿里通义** | `sk-...` | DashScope 控制台 |

#### 在请求里怎么用

API Key 通过 HTTP 请求头传给厂商，两种常见写法：

**方式一：SDK 自动处理（推荐）**

```python
from openai import OpenAI

client = OpenAI(
    api_key="你的API_KEY",           # ← 就是这里
    base_url="https://open.bigmodel.cn/api/paas/v4/",
)
```

**方式二：HTTP 原始请求**

```http
POST /chat/completions HTTP/1.1
Host: open.bigmodel.cn
Authorization: Bearer 你的API_KEY    ← Key 放在 Authorization 头
Content-Type: application/json
```

SDK 会把 `api_key` 自动转成 `Authorization: Bearer <key>`，你不需要手写 HTTP 头。

#### 本仓库怎么配

项目用**环境变量**存 Key，避免写死在代码里或提交到 Git：

```bash
# .env 文件（不要提交 Git）
ZHIPUAI_API_KEY=你的智谱API_Key
```

```python
# open_api_demo.py
import os
api_key = os.getenv("ZHIPUAI_API_KEY")
if not api_key:
    raise ValueError("请先设置环境变量 ZHIPUAI_API_KEY")
```

#### 接入三要素

调用任意一家大模型 API，通常只需三个配置：

```
┌─────────────┬──────────────────────────────────────────────┐
│  api_key    │  你是谁（鉴权）                               │
│  base_url   │  请求发到哪（厂商服务器地址）                  │
│  model      │  用哪个模型（如 glm-4-plus、gpt-4o）          │
└─────────────┴──────────────────────────────────────────────┘
         换厂商往往只改这三项，业务代码不变
```

#### API Key vs 文本 Token（再强调一次）

| | **API Key** | **Token（文本单元）** |
|---|-------------|----------------------|
| **是什么** | 访问接口的密码 | 文本切分后的块 |
| **从哪来** | 厂商控制台创建 | Tokenizer 对文本分词 |
| **用在哪** | 请求头 `Authorization` | 请求体 `messages` 里的文字 |
| **数量** | 通常 1 个 Key 用很久 | 每次调用消耗几千~几百万 |
| **和钱的关系** | 不直接计费，但关联你的账户 | 按 Token 数 × 单价计费 |
| **泄露后果** | 别人盗刷你的余额 | 无此概念 |

#### 安全规范（必做）

| 规则 | 说明 |
|------|------|
| **不要写进代码** | 用环境变量或密钥管理服务，本仓库用 `.env` |
| **不要提交 Git** | `.gitignore` 已忽略 `.env`；Key 进仓库 = 公开泄露 |
| **不要发到聊天/截图** | 复制 Key 时注意遮挡 |
| **泄露后立即轮换** | 在控制台删除旧 Key、创建新 Key |
| **按环境分 Key** | 开发 / 测试 / 生产用不同 Key，便于限流与对账 |
| **设用量上限** | 多数平台可设月度预算或告警，防止盗刷 |

#### 常见问题

| 问题 | 答案 |
|------|------|
| API Key 要花钱吗？ | **创建 Key 免费**；调用模型按 Token 从账户余额扣费 |
| 一个 Key 能调多个模型吗？ | **能**。同一厂商下换 `model` 参数即可 |
| 本地 Ollama 需要 Key 吗？ | **通常不需要**，`api_key` 可填任意占位符 |
| Key 会过期吗？ | 视厂商而定；长期不用建议定期检查，泄露后随时可作废重建 |

### 1.12 SDK 有什么用

有了 **API Key** 和 **Base URL**，你已经具备调用大模型的凭证和地址。接下来需要一种**写代码的方式**把请求发出去——这就是 **SDK** 的用武之地。

#### 一句话定义

> **SDK（Software Development Kit，软件开发工具包）** 是厂商或社区提供的**封装好的代码库**，帮你用几行高级代码完成 HTTP 请求、鉴权、解析响应等脏活累活，而不必手写 URL、请求头、JSON。

可以把它理解为：**API 的「官方遥控器」**——你按按钮（调函数），SDK 帮你处理底层的网络通信细节。

#### 没有 SDK vs 有 SDK

同样发一次对话请求，对比两种写法：

**不用 SDK：手写 HTTP（繁琐、易错）**

```python
import requests
import json

response = requests.post(
    "https://open.bigmodel.cn/api/paas/v4/chat/completions",
    headers={
        "Authorization": f"Bearer {api_key}",
        "Content-Type": "application/json",
    },
    json={
        "model": "glm-4-plus",
        "messages": [{"role": "user", "content": "你好"}],
        "temperature": 0.7,
    },
    timeout=60,
)
data = response.json()
text = data["choices"][0]["message"]["content"]
usage = data.get("usage")
# 还要自己处理：401 鉴权失败、429 限流、5xx 重试、JSON 解析异常……
```

**用 SDK：几行搞定（本仓库方式）**

```python
from openai import OpenAI

client = OpenAI(api_key=api_key, base_url="https://open.bigmodel.cn/api/paas/v4/")
response = client.chat.completions.create(
    model="glm-4-plus",
    messages=[{"role": "user", "content": "你好"}],
    temperature=0.7,
)
print(response.choices[0].message.content)
print(response.usage)  # 直接拿到结构化对象
```

同样的功能，SDK 把**鉴权头、JSON 序列化、响应解析、类型提示**都包好了。

#### SDK 帮你做了哪些事

| 能力 | 不用 SDK | 用 SDK |
|------|----------|--------|
| **鉴权** | 手动拼 `Authorization: Bearer ...` | 传入 `api_key` 即可 |
| **请求体** | 手写 JSON 字典，字段名易拼错 | 参数有命名提示，IDE 可补全 |
| **响应解析** | 自己 `json()` + 多层下标取值 | 返回对象，如 `response.choices[0].message.content` |
| **流式输出** | 自己处理 SSE 数据流 | `stream=True` 一行开启 |
| **错误处理** | 自己判断 HTTP 状态码 | 抛出统一异常（如 `RateLimitError`） |
| **重试** | 自己写退避逻辑 | 部分 SDK 内置或可配置 |
| **切换厂商** | 换 URL、改字段、重写解析 | 往往只改 `base_url` + `model` |

#### 本仓库用的 SDK

| SDK / 库 | 安装 | 用途 |
|----------|------|------|
| **`openai`（Python）** | `pip install openai` | **调用大模型 API**（智谱、DeepSeek 等 OpenAI 兼容厂商） |
| **`transformers`（Hugging Face）** | `pip install transformers` | **本地 Token 估算**（`open_api_demo.py` 中的 Tokenizer） |

两者分工不同：

```
openai SDK     →  发请求、拿回复、读 usage（线上推理）
transformers   →  离线分词、估 Token（成本控制，不调用模型）
```

#### 为什么选 OpenAI SDK 作为默认

全球多数厂商提供 **OpenAI 兼容接口**——路径、字段与 OpenAI 一致。因此：

```python

# OpenRouter —— 聚合多厂商，model 用 openai/gpt-4o 等格式（见 §1.10 OpenRouter 详解）

# 本地 Ollama —— 同样

```

| 限制 | 说明 | 应对思路 |
|------|------|----------|

| **知识截止** | 训练数据有时间边界 | 联网搜索、工具调用补充 |

| **延迟** | 生成长回复需要时间 | 流式输出（Streaming）改善体验 |

## 2. LLM 核心原理

> 第 1 节回答了「大模型是什么」；本节深入「大模型怎么学、怎么算、怎么生成」。
> 掌握这些原理，能帮你理解 API 参数含义、Token 计费逻辑，以及 Agent 开发中的诸多「怪现象」。

### 2.1 整体原理：语言建模

LLM 的本质是一个**条件概率模型**。给定已有 Token 序列 $x_1, x_2, ..., x_t$，预测下一个 Token $x_{t+1}$ 的概率分布：

```
P(x_{t+1} | x_1, x_2, ..., x_t)
```

整段文本的联合概率，通过链式法则分解为逐 Token 预测之积：

```
P(x_1, x_2, ..., x_n) = P(x_1) · P(x_2|x_1) · P(x_3|x_1,x_2) · ... · P(x_n|x_1,...,x_{n-1})
```

**训练目标**：最大化训练语料上每个 Token 的预测正确率（最小化交叉熵损失）。

**推理过程**：自回归（Autoregressive）——每生成一个 Token，把它拼回输入，再预测下一个，直到遇到结束符或达到长度上限。

```
输入:  "今天天气"
  → 预测 P(很|今天天气) = 0.42  → 选中 "很"
  → 预测 P(好|今天天气很) = 0.67 → 选中 "好"
  → 预测 P(。|今天天气很好) = 0.55 → 选中 "。"
  → 结束
输出:  "今天天气很好。"
```

对话、写代码、做推理，底层都是同一条**自回归预测链**；区别只在于 Prompt 把模型「引导」到了不同的概率分布区域。

### 2.2 Token：模型眼中的「词」

> 入门概念见 **§1.6 什么是 Token**；本节补充分词算法与工程细节。

模型不直接处理文字，而是处理 **Token**——词表（Vocabulary）中的整数 ID。

#### 2.2.1 分词（Tokenization）

**Tokenizer** 负责文本 ↔ Token ID 的双向转换。主流算法是 **BPE（Byte Pair Encoding）**：

1. 从字符级词表出发，统计语料中最高频的相邻字符对；
2. 反复合并，直到词表达到目标大小（如 50K ~ 150K）；
3. 常见词整词保留，罕见词拆成子词（subword）。

```
"人工智能"  →  ["人工", "智能"]     → [1234, 5678]
"ChatGPT"    →  ["Chat", "G", "PT"]  → [9012, 345, 678]
"unhappiness"→  ["un", "happiness"]  → [111, 2222]
```

#### 2.2.2 为什么 Token 很重要

| 影响 | 说明 |
|------|------|
| **计费** | API 按 Token 数收费，中英文、代码的 Token 密度差异很大 |
| **上下文窗口** | 128K 窗口 = 最多 128K 个 Token，不是 128K 个汉字 |
| **截断** | 超长输入会被截断或报错，需要先估算 Token 数 |
| **模型差异** | 不同厂商 Tokenizer 不同，同一段文字 Token 数可能不同 |

> 仓库 `open_api_demo.py` 用 Hugging Face Tokenizer 本地估算 Token，再与 API 返回的 `usage` 对比——正是因为 Token 计数直接影响成本与上下文管理。

#### 2.2.3 中文 vs 英文的 Token 效率

| 文本 | 大约 Token 数 | 说明 |
|------|--------------|------|
| 100 个英文单词 | ~130 Token | 英文 1 词 ≈ 1~1.3 Token |
| 100 个汉字 | ~150~200 Token | 中文 1 字 ≈ 1.5~2 Token，效率偏低 |
| 100 行 Python 代码 | ~800~1200 Token | 符号、缩进也会占 Token |

### 2.3 Transformer：LLM 的骨架

2017 年 Google 论文 *Attention Is All You Need* 提出 **Transformer**，取代了 RNN/LSTM，成为现代 LLM 的通用骨架。

#### 2.3.1 Self-Attention（自注意力）

Self-Attention 让序列中**每个 Token 都能直接「看到」所有其他 Token**，并计算关联强度：

```
Query (Q):  「我在找什么信息？」
Key   (K):  「我能提供什么信息？」
Value (V):  「我的实际内容是什么？」

Attention(Q,K,V) = softmax(QK^T / √d_k) · V
```

直觉理解：生成「它」这个词时，模型通过 Attention 找到前文「苹果」并建立指代关系——这是 RNN 难以高效做到的长距离依赖。

```
输入:  [苹果] [很] [甜] [我] [喜欢] [吃] [它]
                                    ↑
                          「它」的 Attention 权重
                          主要落在「苹果」上
```

#### 2.3.2 Multi-Head Attention（多头注意力）

单头 Attention 只学一种关联模式；**多头**让模型并行学习多种模式：

| 注意力头 | 可能学到的模式 |
|----------|----------------|
| Head 1 | 语法结构（主谓宾） |
| Head 2 | 指代关系（它 → 苹果） |
| Head 3 | 相邻词搭配（「人工」+「智能」） |
| Head 4 | 位置邻近性 |

GPT-4 级别模型通常有 **32~128 个注意力头**，每层 Transformer Block 都包含一次 Multi-Head Attention。

#### 2.3.3 Transformer Block 完整结构

一个 Decoder Block 由以下组件组成（按数据流顺序）：

```
输入 Token Embedding + 位置编码
         │
         ▼
┌─────────────────────────┐
│  Multi-Head Self-Attn   │  ← 每个 Token 看全局上下文
│  + 残差连接 + LayerNorm │
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│  Feed-Forward Network   │  ← 两层全连接，非线性变换
│  + 残差连接 + LayerNorm │
└───────────┬─────────────┘
            ▼
       下一层 Block（重复 N 次，N = 32~128 层）
            ▼
       输出 logits → softmax → 下一个 Token 概率
```

关键设计：

- **残差连接（Residual）**：缓解深层网络梯度消失，使百层堆叠成为可能。
- **Layer Normalization**：稳定训练，加速收敛。
- **FFN**：通常占模型 **2/3 参数量**，是「记忆知识」的主要载体之一。

#### 2.3.4 位置编码（Positional Encoding）

Attention 本身不感知 Token 顺序，必须额外注入位置信息：

| 方案 | 代表模型 | 特点 |
|------|----------|------|
| **绝对位置编码** | 原始 Transformer | 固定正弦函数 |
| **RoPE（旋转位置编码）** | LLaMA、Qwen、GLM | 当前主流，外推性较好 |
| **ALiBi** | MPT、BLOOM | 通过 Attention 偏置注入位置 |

RoPE 使模型能区分「猫追狗」和「狗追猫」——词相同，顺序不同，语义完全不同。

#### 2.3.5 因果掩码（Causal Mask）

Decoder-only 模型在训练时使用**三角掩码**，确保预测第 $t$ 个 Token 时只能看到 $1 \sim t-1$，不能「偷看」未来：

```
      t1  t2  t3  t4
 t1  [ ✓   ✗   ✗   ✗ ]
 t2  [ ✓   ✓   ✗   ✗ ]
 t3  [ ✓   ✓   ✓   ✗ ]
 t4  [ ✓   ✓   ✓   ✓ ]
```

这保证了训练和推理的一致性：推理时本来就没有未来 Token 可看。

#### 2.3.6 主流架构对比

| 架构 | 结构 | 代表 | 适用 |
|------|------|------|------|
| **Encoder-only** | 双向 Attention | BERT | 分类、Embedding |
| **Decoder-only** | 因果单向 Attention | GPT、LLaMA、GLM | **文本生成、Chat API** |
| **Encoder-Decoder** | 编码器 + 解码器 | T5、BART | 翻译、摘要 |

当前 Chat API 调用的大模型 **99% 是 Decoder-only**——你发 messages，模型自回归生成回复。

### 2.4 训练全流程

一个可用的 Chat 模型通常经历四个阶段：

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  预训练       │ →  │  有监督微调   │ →  │  对齐        │ →  │  推理部署     │
│ Pre-training │    │ SFT          │    │ RLHF / DPO   │    │ Inference    │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
  学语言规律          学听指令            学人类偏好          API 提供服务
  成本最高            成本中等            成本较低            按 Token 计费
```

#### 2.4.1 预训练（Pre-training）

| 项目 | 内容 |
|------|------|
| **数据** | 网页、书籍、论文、代码、多语言语料，数 TB 级 |
| **任务** | 纯 Next Token Prediction，无人工标注 |
| **目标** | 学会语法、常识、代码模式、多语言 |
| **成本** | 数千~数万 GPU·月，仅大厂可承担 |

预训练完成后得到 **Base Model**——能续写文本，但不会对话、不遵循指令。你直接调 API 用的不是 Base Model。

#### 2.4.2 有监督微调（SFT, Supervised Fine-Tuning）

| 项目 | 内容 |
|------|------|
| **数据** | 人工编写的 (指令, 理想回复) 对，数十万~数百万条 |
| **任务** | 给定用户指令，生成高质量回复 |
| **效果** | 模型从「续写器」变成「对话助手」 |

```
输入:  {"role": "user", "content": "用 Python 写快速排序"}
目标:  {"role": "assistant", "content": "def quicksort(arr): ..."}
```

SFT 决定了模型的**基本能力边界**——能写代码、能翻译、能总结，但可能还不够「有用」或「安全」。

#### 2.4.3 对齐（Alignment）

| 方法 | 全称 | 原理 |
|------|------|------|
| **RLHF** | Reinforcement Learning from Human Feedback | 人类标注回复好坏 → 训练奖励模型 → 强化学习优化 |
| **DPO** | Direct Preference Optimization | 直接从偏好对（好回复 vs 差回复）优化，无需奖励模型 |
| **RLAIF** | RL from AI Feedback | 用 AI 代替人类做偏好标注，降低成本 |

对齐解决的核心问题：

- 减少有害、偏见、幻觉输出
- 提升遵循指令、拒绝越界请求的能力
- 让回复风格更符合人类期望（简洁、有帮助、诚实）

> 你感受到的「GPT 很有礼貌」「Claude 很谨慎」，主要源于对齐阶段，而非预训练本身。

#### 2.4.4 推理增强训练（可选）

以 OpenAI o1/o3、DeepSeek-R1 为代表的**推理模型**，额外引入：

- **Chain-of-Thought 数据**：分步推理过程作为训练样本
- **过程奖励（Process Reward）**：不只看最终答案，还奖励正确的中间推理步骤
- **Test-Time Compute**：推理时生成更长的「思考链」再输出答案

这类模型在数学、代码、逻辑任务上显著更强，但 Token 消耗和延迟也更高。

#### 2.4.5 学习语料量级

LLM 的「知识」全部来自训练语料。不同阶段的语料**量级差异极大**——预训练占 99% 以上，SFT 和对齐只是「精修」。

##### 各阶段语料对比

| 阶段 | 语料量级 | 数据形态 | 作用 |
|------|----------|----------|------|
| **预训练** | **数千亿 ~ 数十万亿 Token**（TB 级原始文本） | 网页、书籍、论文、代码、对话片段 | 学习语言规律与世界知识 |
| **SFT** | **10 万 ~ 1000 万条**指令样本 | 人工编写的 (问题, 理想回答) 对 | 学会听指令、对话格式 |
| **对齐（RLHF/DPO）** | **1 万 ~ 100 万条**偏好对比 | (问题, 好回答, 差回答) 三元组 | 优化有用性、安全性、风格 |
| **推理增强** | **数十万 ~ 数百万条**CoT 样本 | 带分步推理过程的问答 | 强化复杂推理能力 |

```
预训练语料  ████████████████████████████████████████  ~99%+
SFT 语料    █                                         ~0.x%
对齐语料    ▏                                         ~0.0x%
```

##### 预训练语料：Token 数 vs 参数量

业界经验（**Chinchilla 缩放定律**，DeepMind 2022）：给定算力预算，模型参数量与训练 Token 数存在最优比例——

```
最优训练 Token 数 ≈ 20 × 参数量（单位：个）
```

| 参数量 | Chinchilla 建议 Token 数 | 约等于文本量 |
|--------|--------------------------|--------------|
| 7B（70 亿） | ~140B（1400 亿）Token | ~280 GB 纯文本 |
| 70B（700 亿） | ~1.4T（1.4 万亿）Token | ~2.8 TB 纯文本 |
| 405B | ~8T Token | ~16 TB 纯文本 |

早期模型（如 GPT-3 175B）训练 Token 偏少（~300B），属于「大模型、少数据」；2023 年后主流趋向 **「小模型、多数据」** 或 **「大模型、更多数据」**，同等参数下能力更强。

##### 代表性模型的公开语料规模

| 模型 | 参数量 | 预训练 Token 量 | 备注 |
|------|--------|-----------------|------|
| GPT-2 | 1.5B | ~40 GB 文本（~100 亿 Token 级） | 早期探索 |
| GPT-3 | 175B | ~300B Token | 未达 Chinchilla 最优比 |
| BLOOM | 176B | 350B Token | 多语言开源 |
| LLaMA 1 | 65B | 1.4T Token | 接近 Chinchilla 最优 |
| LLaMA 2 | 70B | 2T Token | 数据量提升 |
| LLaMA 3 | 8B ~ 405B | ~15T Token | 2024 头部开源标杆 |
| Qwen 2.5 | 0.5B ~ 72B | ~18T Token | 中文语料占比高 |
| DeepSeek-V3 | 671B（MoE） | 14.8T Token | 含大量代码与推理数据 |
| GPT-4 / Claude 4 | 未公开 | 据估 10T+ Token | 闭源，仅推测 |

> 闭源商业模型（GPT-4、Claude、GLM-4 等）极少公开精确语料量，上表以**已披露的开源模型**为参考锚点。

##### 预训练语料的组成（典型比例）

```
┌─────────────────────────────────────────────────────┐
│  网页爬取（Common Crawl 等）     50% ~ 70%           │
│  代码（GitHub 等）               5%  ~ 15%           │
│  书籍 / 论文 / 百科              10% ~ 20%           │
│  对话 / 论坛 / 社交媒体          5%  ~ 15%           │
│  多语言（含中文）                视模型定位而定         │
└─────────────────────────────────────────────────────┘
```

语料在入库前经历严格**清洗与去重**：

- 过滤低质量网页、spam、重复内容
- 去除个人隐私与有害信息（程度因厂商而异）
- 同一内容多次出现只计一次，实际有效 Token 远小于原始爬取量

原始爬取 **10 TB** 文本，清洗去重后可能只剩 **1~2 TB** 有效语料。

##### 语料量级对开发者的含义

| 现象 | 与语料的关系 |
|------|--------------|
| **知识截止** | 预训练语料有时间边界，之后的事件模型未见过 |
| **中文能力差异** | 中文语料占比高的模型（Qwen、GLM）中文更强 |
| **代码能力差异** | 代码语料占比影响 Copilot 类能力（DeepSeek-Coder、Codex） |
| **幻觉** | 语料中没有的信息，模型仍会「编造」——它学的是统计规律，不是事实库 |
| **SFT 不能补知识** | 微调教的是「怎么说」，不是「知道什么」；补知识靠 RAG 或继续预训练 |

##### 一条直觉

> **参数量决定模型「脑容量」，语料 Token 量决定「读了多少书」。**
> 只增大其中一个，收益都会递减；当代 LLM 的竞争，很大程度上是**谁能用更多高质量 Token 把参数量「喂饱」**。

### 2.5 推理原理：从 Prompt 到回复

调用 Chat API 时，服务端实际执行两阶段：

```
┌─────────────────────────────────────────────────────────┐
│  Phase 1: Prefill（预填充）                              │
│  一次性并行处理所有输入 Token（system + history + user）  │
│  计算并缓存每层的 Key / Value → KV Cache                 │
├─────────────────────────────────────────────────────────┤
│  Phase 2: Decode（解码）                                 │
│  逐 Token 自回归生成：                                    │
│    每步只算 1 个新 Token，复用 KV Cache，避免重复计算      │
│    直到 EOS 或达到 max_tokens                            │
└─────────────────────────────────────────────────────────┘
```

#### 2.5.1 KV Cache

自回归生成时，每步都要对**全部历史 Token** 做 Attention。KV Cache 缓存历史 Token 的 Key/Value 向量，新 Token 只需与缓存做 Attention，复杂度从 O(n²) 逐步计算降为 O(n) 增量计算。

| 阶段 | 计算特点 | 计费 |
|------|----------|------|
| **Prefill** | 并行，计算密集 | 计入 prompt_tokens |
| **Decode** | 串行，每步 1 Token | 计入 completion_tokens |

这就是为什么：**输入很长时首 Token 延迟高（Prefill 慢），生成阶段逐字流出（Decode 稳态）**——Streaming 正是在 Decode 阶段逐 Token 推送。

#### 2.5.2 采样策略（决定「选哪个 Token」）

模型输出的是词表上的概率分布，如何从分布中选出下一个 Token，由采样策略决定：

| 策略 | 行为 | 对应 API 参数 |
|------|------|---------------|
| **Greedy** | 永远选概率最高的 Token | `temperature = 0` |
| **Temperature Sampling** | 用温度缩放概率后再采样 | `temperature`（0~2） |
| **Top-K** | 只从概率最高的 K 个 Token 中采样 | `top_k`（部分厂商支持） |
| **Top-P（Nucleus）** | 从累积概率达 P 的最小 Token 集合中采样 | `top_p`（0~1） |

```
原始概率:  [好: 0.40] [很: 0.25] [不: 0.15] [太: 0.10] [其他: 0.10]

temperature = 0   →  选「好」（确定性，适合代码/JSON）
temperature = 0.7   →  大概率选「好」，偶尔选「很」（默认对话）
temperature = 1.5   →  分布更平，输出更多样（创意写作）

top_p = 0.9         →  只从累积 90% 概率的 Token 中采样，砍掉长尾噪声
```

**工程建议**：

- 需要稳定、可复现输出 → `temperature=0`，必要时加 `seed`（厂商支持时）
- 日常对话 → `temperature=0.7~1.0`
- 结构化输出（JSON）→ `temperature=0` + JSON Mode / Schema 约束

### 2.6 上下文窗口与长文本

**上下文窗口（Context Window）** = 模型单次能处理的最大 Token 数（输入 + 输出之和）。

| 模型级别 | 典型窗口 | 约等于 |
|----------|----------|--------|
| 入门级 | 8K ~ 32K | 1~2 万字中文 |
| 主流 | 128K | 8~10 万字 |
| 超长 | 1M（Gemini） | 70~80 万字 |

窗口不是「硬盘容量」——Attention 计算量随长度平方增长，超长上下文成本显著上升。部分厂商对超过 128K 的部分**单独加价**。

长上下文的实现技术：

- **RoPE 外推 / NTK-aware 插值**：扩展位置编码支持范围
- **稀疏 Attention**：不是所有 Token 两两互看，降低计算量
- **滑动窗口 Attention**：如 Mistral 的 SWA，局部窗口 + 全局 Token

### 2.7 涌现能力与 Scaling Law

#### 2.7.1 Scaling Law（缩放定律）

OpenAI 2020 年研究发现：模型性能与**参数量、数据量、算力**呈幂律关系——三者同步放大，Loss 持续下降。

```
性能 ↑                          小模型: 只会补全
  │                            中模型: 能对话
  │         ╱                  大模型: 推理、代码、工具调用
  │       ╱                    ↑ 这些能力在较小规模时几乎不存在
  │     ╱                      称为「涌现能力（Emergent Abilities）」
  │   ╱
  └──────────→ 模型规模
```

#### 2.7.2 常见涌现能力

| 能力 | 说明 |
|------|------|
| **In-Context Learning** | 无需更新权重，仅靠 Prompt 中的示例学会新任务（Few-shot） |
| **Chain-of-Thought** | 提示「请一步步思考」后，推理能力显著提升 |
| **Instruction Following** | 理解并执行复杂、多步骤指令 |
| **Tool Use** | 判断何时需要调用外部工具、如何构造参数 |

这些能力无法靠简单堆规则实现，是大规模预训练 + 对齐的自然结果——也是 AI Agent 可行的根本原因。

### 2.8 原理 → API 行为对照表

将原理映射到你日常调 API 时会遇到的现象：

| 原理 | API / 工程现象 |
|------|----------------|
| Next Token Prediction | 模型「停不下来」、需要 `max_tokens` 限制长度 |
| 自回归 Decode | 回复越长延迟越高；Streaming 逐 Token 返回 |
| KV Cache | 长 Prompt 首 Token 慢；相同前缀重复调用可受益缓存（部分厂商） |
| Temperature / Top-P | 同一 Prompt 多次调用结果不同 |
| 上下文窗口 | 历史太长被截断；需裁剪或摘要 |
| SFT + 对齐 | System Prompt 有效；模型会拒绝违规请求 |
| 预训练知识截止 | 不知道训练截止日期之后的事件 |
| Token 计费 | 中英文、代码 Token 密度不同；应用本地估算 |

### 2.9 推理时的关键参数（预告）

后续文档 02 会详解各参数，此处结合原理做速查：

| 参数 | 原理关联 | 作用 |
|------|----------|------|
| `temperature` | 采样策略 | 控制概率分布平滑度；0 = 确定性 |
| `max_tokens` | 自回归终止条件 | 限制 Decode 阶段生成长度 |
| `top_p` | Nucleus Sampling | 截断低概率长尾 Token |
| `stop` | 终止符 | 遇到指定字符串停止 Decode |
| `stream` | Decode 阶段 | 每生成 1 Token 即推送，降低首字延迟感知 |
| `messages` | 完整上下文输入 | 触发 Prefill，全部计入 prompt_tokens |

### 3.1 第一梯队概览（2025–2026）

> 下表「开放程度」列标注各厂商主要模型的开源/闭源属性，详见 §1.9。

| 厂商 | 代表模型 | 开放程度 | API 特点 | 备注 |
|------|----------|----------|----------|------|
| **OpenAI** | GPT-4o、o1/o3 | 闭源 | 事实上的行业标准，生态最完善 | 国内访问需代理 |
| **Anthropic** | Claude 3.5/4 Sonnet | 闭源 | 长上下文、代码与写作能力强 | 安全对齐做得好 |
| **Google** | Gemini 1.5/2.0 | 闭源 | 原生多模态，超长上下文（1M Token） | Vertex AI 企业向 |
| **智谱 AI** | GLM-4 系列 | 混合（部分开源 + API） | **OpenAI 兼容接口**，国内直连 | 本仓库默认接入厂商 |
| **阿里通义** | Qwen 2.5/3 | 混合（开源 + API） | 中文表现优秀 | DashScope 平台 |
| **DeepSeek** | DeepSeek-V3/R1 | 混合（开源 + API） | 性价比极高，推理模型领先 | 权重可本地部署 |
| **Meta** | LLaMA 3.x | 开源 | 需自行部署 | 无官方商业 API |
| **Mistral** | Mistral Large | 混合 | OpenAI 兼容 | 欧盟数据合规 |
| **OpenRouter** | 聚合 GPT/Claude/Gemini 等 | 聚合平台 | **一个 Key 调多厂商**，OpenAI 兼容 | 见 §1.10 ③ OpenRouter 详解 |

### 3.2 OpenAI 兼容接口成为事实标准

越来越多厂商提供与 OpenAI Chat Completions **相同路径、相同字段** 的 API：

```python
from openai import OpenAI

client = OpenAI(
    api_key="YOUR_KEY",
    base_url="https://open.bigmodel.cn/api/paas/v4/",  # 只需换 base_url
)

response = client.chat.completions.create(
    model="glm-4-plus",
    messages=[{"role": "user", "content": "你好"}],
)
```

这意味着：**学会一套 SDK，即可切换多家厂商**，是本仓库 Phase 1 的核心工程策略。

OpenRouter 是这一策略的**极端体现**——不仅换 `base_url`，连 `model` 也可在同一 Client 下切换 `openai/gpt-4o`、`anthropic/claude-3.5-sonnet`、`deepseek/deepseek-chat` 等，无需维护多套 Key 与 SDK。

## 4. 选型思路

### 4.1 按场景选型

| 场景 | 推荐方向 |
|------|----------|
| 国内生产环境、低延迟 | 智谱 GLM、通义 Qwen、DeepSeek |
| 快速对比 GPT / Claude / Gemini | **OpenRouter**（一个 Key，换 model 即可） |
| 复杂推理、Agent 规划 | GPT-4o、Claude Sonnet、DeepSeek-R1 |
| 超长文档处理 | Gemini 1.5 Pro、Claude（200K 上下文） |
| 成本敏感、高并发 | DeepSeek-V3、GLM-4-Flash |
| 数据不出境 | 本地部署 Qwen / LLaMA / DeepSeek |

### 4.2 选型检查清单

- [ ] 是否提供 OpenAI 兼容 API？
- [ ] 国内网络是否可达（延迟、稳定性）？
- [ ] 上下文窗口是否满足业务（32K / 128K / 1M）？
- [ ] 是否支持 Function Calling / JSON Mode / Streaming？
- [ ] Token 单价与免费额度？
- [ ] 数据合规与隐私政策？

### 4.3 本仓库的学习默认

| 项目 | 选择 | 原因 |
|------|------|------|
| 主力 API | 智谱 GLM-4 | 国内直连、OpenAI 兼容、注册门槛低 |
| 海外模型对比（可选） | OpenRouter | 一个 Key 试 GPT/Claude/Gemini，SDK 代码不变 |
| SDK | `openai` Python 包 | 行业标准，切换厂商零成本 |
| Token 估算 | Hugging Face `transformers` | 本地预估 vs 接口 usage 对比 |

## 5. 小结

| 要点 | 内容 |
|------|------|
| **大模型是什么** | 超大规模神经网络，通过预测下一个 Token 实现语言理解与生成 |
| **什么是 Token** | 模型处理文本的最小单元，不等于字或词；决定计费、窗口与截断 |
| **Token 成本直觉** | 《红楼梦》73 万字 ≈ 50~60 万 Token；DeepSeek ~1–2 元，GPT-4o 可达 60 元+ |
| **什么是 API Key** | 调用 API 的鉴权密钥（如 `sk-xxx`），与文本 Token 无关；配在 `.env` 中 |
| **SDK 有什么用** | 封装 HTTP/鉴权/解析，本仓库默认 `openai` SDK，换 `base_url` 切厂商 |
| **三大核心能力** | 语言理解（读懂）→ 知识推理（想清楚）→ 语言生成（说出来） |
| **开源 vs 闭源** | 开源可本地部署与微调；闭源通过 API 调用、能力上限更高 |
| **接入渠道** | 官方 API / 云平台 / **OpenRouter 聚合** / 本地部署 / 托管推理 / 框架路由 |
| **LLM 核心原理** | 语言建模 → Token/BPE → Transformer → 预训练/SFT/对齐 → 语料量级 → Prefill+Decode 推理 |
| **为什么重要** | AI Agent 的推理核心，API 化后可直接嵌入应用 |
| **如何接入** | Phase 1 默认渠道 ① 智谱官方 API；换 `base_url` 可切换厂商或本地 Ollama |
| **下一步** | 阅读文档 02（API 规范）、运行 `open_api_demo.py` 完成首次调用 |
